# Shipping

## Порядок

1. **Проверка.** Последний `verifier` должен быть `PASS` после последних правок. Иначе — запусти `verifier`; при FAIL стоп.
2. **Ветка.** `git branch --show-current`. Если `main`/`master`/`develop` — создай `feature/<slug>` (фича) или `fix/<slug>` (баг); slug — из ID плана. Если в репозитории другой нейминг веток (`git branch -a`) — следуй ему.
3. **Состав.** `git status`. Добавляй файлы явно по именам, не `git add -A`. Не добавляй:
   - `docs/plans/` — если в `CLAUDE.md` проекта не сказано обратное;
   - локальные и сгенерированные файлы, секреты, `.env`, IDE-файлы.
4. **Сообщение.** Формат как в `git log --oneline -20`. Если формата нет — Conventional Commits: `feat|fix|test|refactor(scope): <что>`. Ключ задачи — в сообщении, если есть (как принято в репо). Тело — 1–3 строки «зачем», если не очевидно.
5. **Коммит.** Без `--no-verify`, без `--amend` чужих коммитов. Падает pre-commit hook — исправь причину и сделай новый коммит.
6. **Push.** `git push -u origin <branch>`.
   - Никогда не пушить в `main`/`master`.
   - Никогда `--force`/`-f`/`--force-with-lease`.
   - Push отклонён (non-fast-forward) — стоп и доложи, не перезаписывай.
7. **Итог:** ветка, хеш и сообщение коммита, ссылка на создание MR/PR, если git её вывел.
