# Planning

План — главный артефакт флоу. По нему пишут код без дополнительных вопросов.

## Порядок

1. **ID.** Ключ задачи, если есть (`ABC-123`), иначе slug из 2–5 слов kebab-case. Файл: `docs/plans/<ID>.md`. Если файл уже есть — это правка плана.
2. **Контекст проекта.** Прочитай раздел `## ccaf` в `CLAUDE.md`.
3. **Анализ.** Вызови агента `analyst`, если код незнакомый, задача задевает больше одного модуля или это баг. Иначе изучи сам (Grep/Read), но держи контекст узким.
4. **Вопросы.** Если есть неясности, которые меняют решение, — задай их одним нумерованным списком, к каждому — варианты и твоя рекомендация. Стоп до ответа. Не спрашивай то, что видно из кода. Не додумывай.
5. **План** по шаблону [plan-template.md](plan-template.md). Объём — пропорционален задаче: мелкой задаче — короткий план.
6. **Самопроверка** (ниже). Исправь, что не проходит.
7. **Выдача.** Покажи пользователю выжимку до 15 строк: решение, число шагов, изменения БД/API/контрактов, риски, путь к файлу. Спроси: «Апрув или комментарии?». **Стоп.**
8. **Апрув.** Поставь `Статус: approved`. Правки — в тот же файл, затем покажи, что изменилось.

## Правила содержания

- **Решение:** одно, кратко и почему так. Отвергнутые альтернативы — одной строкой, если важны.
- **Шаги атомарные:** один шаг = один файл/класс + что именно меняется + проверяемый результат.
  `- [ ] 3. \`order/OrderService.java\` — метод cancel(id): статус CANCELLED, событие OrderCancelled. Проверка: модуль order компилируется`
- **Порядок шагов** такой, чтобы код компилировался после каждого: миграция → сущность/модель → репозиторий → сервис → API/листенер → конфиг.
- **Образцы:** для каждого нового класса укажи существующий класс-образец из проекта.
- **Без кода**, кроме сигнатур публичных методов, DTO-полей и SQL-DDL, где они важны.
- **БД:** только новые миграции, никогда не правка применённых. Имя файла по конвенции проекта. Индексы, NOT NULL на существующих таблицах с данными, блокировки на больших таблицах.
- **API и сообщения:** что меняется в контракте, обратная совместимость (новые поля опциональны, старые не удаляются без версии), порядок деплоя продюсер/консьюмер.
- **Конфиги:** новые свойства, значения по умолчанию, профили.
- **Критерии приёмки** проверяемые: «при X → Y», без «корректно работает».
- **Риски** — конкретные (данные, производительность, совместимость, конкурентность), с митигацией.

## Самопроверка

- [ ] каждый шаг указывает конкретный файл и проверку, нет «и т.д.», «при необходимости»;
- [ ] нет шагов вне задачи (рефакторинг, «заодно»);
- [ ] миграции — только новые файлы;
- [ ] изменения контрактов помечены и совместимость описана;
- [ ] открытые вопросы либо закрыты, либо явно блокируют конкретный шаг.
