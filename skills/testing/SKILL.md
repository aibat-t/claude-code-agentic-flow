# Testing

## Правила

- Стек — тот, что уже в проекте. По умолчанию JUnit 5 + Mockito + AssertJ. Новые тестовые библиотеки не добавляй.
- Найди 1–2 существующих теста рядом и повторяй их стиль: расположение, нейминг, базовые классы, фабрики тестовых данных, аннотации.
- Источник тестов — раздел «Критерии приёмки» плана, а не реализация. Каждый критерий → минимум один тест + граничные случаи. Ожидаемые значения берутся из требований.
- Плюс граничные случаи: null/пустое, границы диапазонов, дубликаты, не найдено, исключения зависимостей, повторный вызов (идемпотентность).
- Unit-тест: класс под тестом создаётся напрямую, зависимости — моки. Не поднимай Spring-контекст ради unit-теста. Не мокай value-объекты и DTO.
- Структура: `// given`, `// when`, `// then`. Одна проверяемая вещь на тест.
- Имя описывает поведение: `cancel_whenOrderPaid_refundsAndPublishesEvent` (или формат проекта, `@DisplayName` — если так принято).
- Проверки через AssertJ, исключения — `assertThatThrownBy`. Взаимодействия — `verify` только там, где это суть поведения (отправка события, сохранение).
- Без `Thread.sleep`, без зависимости от порядка тестов, времени и случайности (фиксированный `Clock`, сиды).

## Баг

1. Сначала тест, воспроизводящий баг. Он должен **падать** по ожидаемой причине (подтверди через `verifier`).
2. Потом фикс. Тест становится зелёным, остальные не ломаются.

## Если тест падает из-за кода

Не подгоняй тест под код. Если реализация не соответствует критерию приёмки — сообщи: тест, ожидание, факт. Чинится код, а не тест.
